active-etf-radar：群益來源 API 修復 + Dashboard 表達模式升級

一次例行刷新觸發的兩件事——修好因網站改版而壞掉的群益資料來源，並把只會看「單點」的 dashboard 升級成會說「趨勢」與「結論」。

2026-06-12 專案：active-etf-radar 非交易系統 · 公開資料研究 主控：Claude Code

00一句話總結

例行刷新 7 檔主動 ETF 時發現群益兩檔抓取失敗。診斷出官網改成 JS 渲染、用 Playwright 攔到底層 JSON API 修好；過程順帶抓到一個舊有的資料品質 bug（美股基金持股長期抓不全）。接著把 dashboard 從「快照式」升級成「趨勢式」：加趨勢線、今日結論、事件強度排序、深色 hero。

01背景

今天是回專案的第一步：依 START.md 刷新全部 7 檔主動式 ETF 的最新公開持股。資料距上次（6/8~6/9）已隔 3~4 天。刷新時 EZMoney 三檔、復華、第一金都正常，群益兩檔（00992A、00997A）報錯：群益申購買回清單缺少資料日期。

02問題一：群益官網改 JS 渲染（核心修復）

症狀像「解析 bug」，根因其實是「抓到的頁面內容變了」。

症狀fetch-capital 丟 缺少資料日期，6/9 還正常。
比對今天的 HTML 只有 263KB（6/9 是 417KB），完全沒有 buyback-stocks-section、沒有任何日期、沒有持股關鍵字，只有 noscript。
判定不是解析 bug——群益官網改成前端 JS 渲染，urllib 抓到的是空殼頁。
找 API用 Playwright 載入頁面、攔 network requests，找到資料端點。
修法adapter 從「爬 HTML」改成「打 JSON API」（不需 JS）。

底層 API

  • POST https://www.capitalfund.com.tw/CFWeb/api/etf/buyback
  • body：{"fundId":"<product_id>","date":null}
  • 回傳：data.pcf（含 date1 / date2 / exchangeDesc）+ data.stocks[]（stocNo / stocName / weight / weightRound / share）
  • 資料日沿用舊規則：取 exchangeDesc 括號內的匯率日（等於 date2），與歷史 CSV 一致。

raw 改存 data/raw/capital_buyback/*.json；dataclass 欄位 raw_html_path 改名 raw_path（cli.py 同步）。

經驗 1 · SPA 改版的標準解法

當一個原本能爬的網站突然回傳空殼／少很多內容、且出現 noscript，先別改 parser——用 Playwright 攔 network requests 找底層 API，直接打 JSON 端點。比硬解 JS 或上 headless 渲染更穩、更快、更好維護。

03問題二：美股基金持股長期抓不全（順帶發現）

改用 API 後，00997A（群益美國增長）的持股數對不上歷史：

版本持股數權重合計
舊 HTML parser10 檔40.9%
新 JSON API53 檔93.16%

原因：舊版我一度把明細過濾成「只留台股 4 碼代號」，但這檔含美股、日股、韓股（MU US、4062 JP、009150 KS），整批被砍掉。已改成「有代號＋名稱＋權重就收」；台股 4 碼過濾只用在台股日報排行那一層，不可用在持股明細層。

副作用：換來源那一輪，00997A 的「持股變化／異常加碼」會出現一次性假新增（約 43 檔），下一輪快照自動修正。

經驗 2 · 過濾條件要分層

「只留台股 4 碼代號」是呈現層（台股排行）的規則，不是資料層（持股明細）的規則。把展示用的過濾誤套到原始資料抽取，會在含外股的標的上靜默漏資料。資料層原則：盡量全收，過濾留到呈現層做。

04升級：Dashboard 表達模式（快照 → 趨勢）

最大缺口：已累積 15 個資料日快照，但畫面只表達「最新 vs 前一日」單點，0 條趨勢線。

① 趨勢線（sparkline）

  • 共識持股總表：每列加「近期股數趨勢」，畫該股票在所有持有基金的總股數、近 12 個資料日走勢（聯合資料日 forward-fill），漲綠跌紅。
  • 單基金完整持股表：用該基金自己的股數序列，看單一基金對個股的加減動作。
  • 異常加碼卡：每筆加小尺寸趨勢線。

② 今日結論橫幅

頁面頂端一句白話：今天幾檔新買進進共識／首次納入／異常加碼／同向加股，5 秒判讀「今天有沒有事」。

③ 事件卡強度排序

四張事件卡內容都「最強在最上面」，每張卡第一筆加左側強調條與淡底，眼睛直接落在最該看的那檔。

④ 第一屏深色 NASA hero

標題列＋今日結論做成一整塊深藍漸層 hero（象牙白字＋琥珀數字）；下面查表區維持淺色——密集表格淺色比較好讀，深色只用在 hero。

經驗 3 · 既有資料先榨乾再加功能

升級前先問「現有資料還有哪些沒被表達出來」。這次 15 天快照早就躺在 data/processed/，把它從單點變成趨勢線，不用重抓任何資料就是體驗最大的躍升。先用足現有資料，再談新資料來源。

05驗證與環境踩坑

  • 視覺驗證：file:// 被 Playwright MCP 擋（安全政策）。解法：起本機 python -m http.server → 用 http://127.0.0.1 載入 → 截圖 → 關 server。
  • 輸出亂碼：PowerShell cp950 顯示中文會亂；跑前設 PYTHONIOENCODING=utf-8，資料本身正常。
  • iCloud 暫存：Playwright MCP 會在 iCloud 根目錄留 .playwright-mcp/（console log + page 快照）；py_compile 會寫 __pycache__。屬暫存 churn，用完即清。
